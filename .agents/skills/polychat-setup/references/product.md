# Understand Polychat

Polychat combines personal **Chat** with collaborative **Work**. Start with the web app and API; add sandbox coding, training or native iOS only when needed.

Chat is conversation-first, with personal capabilities and rich experiences below `/chat`. Work organises projects inside workspaces, with shared conversations, instructions, sources, outputs and selected capabilities. Work access requires the appropriate plan and current workspace membership. There is no third global Apps or Recipes mode.

## Choose how work runs

- Use a conversation for interactive work, an experience for a richer workflow, a recipe for reusable configured work, and a project task/flow for durable agent execution and hand-offs.
- Configure skills and saved agents in the capability library. Skills supply instructions; agents supply personas and capability requests. Their runner still needs access to everything they use.
- Keep connector installations and credentials attributable to the person running the work. Project membership does not grant another member's external account.
- Use the project's **Automatic model preference** for its default routing tier. Explicit request tiers or models override it; it is not a spending cap.
- Treat **sources** as durable inputs and **outputs** as durable results. Project scope adds collaboration; conversation links add provenance.
- Show durable output origin from its captured run, effective model/provider, skill revisions, source references and approval outcomes. Label incomplete history as partial or legacy, and never treat an old reference as current access.
- Compare output revisions before restoring supported local text results. Restore appends a revision and preserves provenance; files, connector or publication effects, provider jobs and sandbox repository changes are review-only and need their own external compensation.

For models that support it, the **Processing** selector offers Automatic, Standard and Fast with catalogue pricing. Changing the model clears an explicit choice; web Chat, Work and iOS use the same contract.

Model and capability readiness is a short-lived preflight, not an execution guarantee. Ready, setup-required, unavailable and unknown checks remain distinct and show the next useful action. Removing an account or provider key does not silently replace the selected model: web and iPhone retain it, block sending and ask you to refresh access or choose another model. The server checks current authority again when work starts.

Changing models affects the next run and keeps compatible attachments and the conversation's stored history, but resets model-specific response settings. Finish or cancel an active run, approval or question first. Remove incompatible attachments before switching; start a new conversation for a one-turn image model when the current conversation already has history. Use a branch or second opinion for comparisons so each result keeps its own model attribution and usage identity.

## Find conversations and results

Conversation lists can group ordinary chats and task conversations. In a saved remote conversation, **Branches** opens related threads without copying history. Personal branches remain owner-scoped; project branches remain within the same membership-authorised project. Local-only and iOS navigation do not gain this web branch browser.

Each accepted stored task has one run identity and an authoritative state that is separate from the conversation and its visible assistant messages. Web and iOS preserve that identity, while repeated submissions are only safely deduplicated when they reuse the same command identity. Queue-dispatched project tasks continue independently of the request that starts them. Personal stored Chat remains best-effort after a connection loss, and local-only Chat remains private to the device with no server recovery.

An interrupted connection recovers the same accepted task, including saved tool and partial assistant messages, and keeps observing it until attention or completion is reported. Web and iPhone consume ordered task updates and automatically replace local state with an authoritative snapshot if updates were missed or retained history expired. Repeated or late delivery cannot duplicate visible work or reopen a finished task. Stop targets that task and attempt on either client. A stop request appears before execution has actually stopped, and a tool or provider call already in progress may finish before cancellation becomes final; changing views and stopping voice recording are separate actions. Questions, tool approvals and stage reviews have distinct durable controls rather than being inferred from assistant prose. On iPhone, project-task cards support structured choices, written answers and exact approve or reject actions. They show sending, retryable failure, expiry, resolution on another device and a saved decision whose provider continuation was interrupted. Project-task questions and approvals remain recoverable for seven days; recovery expires older unresolved interactions instead of leaving a dead control. Both clients defer to persisted interaction state, and current workspace membership is checked again for every response.

Project task detail on web and iPhone also shows a durable activity timeline after reopening or switching devices. Proposed outcomes are separate from actual runs, steps, tool lifecycle, questions or approvals and results. Waiting, tool failure, interruption, cancellation and completion remain distinct, while raw tool payloads and private reasoning stay out of the timeline. Web can expand safe summaries; iPhone keeps actionable and terminal entries in its compact view even when the conversation contains long generated text.

A project task keeps the saved flow it started with and shows each stage as proposed, executing, completed, failed, interrupted or abandoned from actual run evidence. Open a stage to reach its exact run conversation or durable result; retries appear as separate attempts with their own provenance. You can edit an untouched pending plan, but cancelling after execution keeps completed evidence and requires a new task for changed work. Polychat retries a failed model-only stage at its existing boundary, but asks you to reconcile an external provider when an approved write may already have happened.

The task inbox on web and iPhone surfaces pending decisions, meaningful failures, assignments and recent useful completions. Read and dismiss affect only your inbox, never the task, and the server checks current membership and task state whenever it lists or opens an item. Notification permission and Polychat registration are separate states: granting browser or iPhone permission does not prove delivery is configured. Preferences apply per account, registrations per installation, and signing out removes only that installation. Push messages use generic copy and resolve to current task state, so an old notification cannot reveal stale detail or restore a finished action.

Stored conversations compact older history when requested or when model context pressure requires it. A snapshot archives only the complete messages supplied to its summary input; messages beyond that bounded input, including an individually oversized message, remain active. Web and iOS compaction status shows how many candidate messages were summarised or preserved verbatim and how many remained active.

Each later model step checks context pressure again. Large tool results are shortened only in the model prompt and remain stored for authorised retrieval; further pressure removes older complete steps before the latest user constraint. Stored-run context views on web and iPhone show attached sources, effective skills, the active summary, omissions and context-window usage. Usage says whether it came from the provider or is an estimate, and omitted text is never described as fully retained. Removing a composer attachment changes the next submitted turn; changing curated project context affects later new project conversations rather than rewriting an existing conversation.

Temporary model rate limits, timeouts, network failures and provider outages can trigger one visible repeat of that model call, with no more than two repeats across a run. Web and iPhone show whether the run is waiting or trying again, and stopping during the wait prevents another attempt. Invalid input, credentials, permissions, policy, conflicts and usage limits do not retry. If an external write loses its response, Polychat reports that it may have completed: explicitly idempotent operations can repeat once with the same parameters, while other writes require you to check the external system first.

Usage is charged to the runner in monthly credits. A stored run shows its reserved estimate separately from recorded consumption and settlement, across all retry attempts. A reservation is not a charge; missing provider usage appears as unknown rather than zero. Workspace owners and administrators can review attributed spend without creating a shared allowance. Read [usage](operations/loop-cost-controls.md) for enforcement and reporting, or [architecture context](architecture/context.md) for the implementation map.

## Use global Attention

Attention brings operational work from every workspace you can currently access into one view. Filter it by needs approval, needs input, in review, failed or stalled, running or recently completed, then narrow by workspace, project, owner, task or coding run, and an inclusive date range. The URL retains those filters, and deterministic pages keep large result sets bounded.

Items come from task interaction state and sandbox-run Activity, not assistant prose. Opening one returns you to its existing task, conversation or project Activity surface to act with the same authority as before. Losing workspace membership removes the item and its filter facets; seeing an item does not grant its runner controls, connector credentials or approval authority. Read [ADR 0050](architecture/decisions/0050-derive-global-attention-from-authoritative-work-state.md) for the read-model boundary.

## Organise conversations

Use a conversation's organise action to pin it, mark it unread, snooze it until tomorrow or the next agent response, and assign labels. Pin, unread and snooze are personal even in a shared project. Active snoozes leave ordinary conversation lists and Attention, but remain searchable so you can find and clear them.

Personal labels belong to you. Project labels are shared only within that project: owners and administrators manage the available labels, while current project members can assign them to conversations they can access. Deleting a label removes its assignments, and none of these controls changes project membership or who can run, approve or connect external accounts. Read [ADR 0051](architecture/decisions/0051-separate-personal-conversation-state-from-project-labels.md) for the ownership boundary.

## Schedule repeatable work

Schedule a recipe from its capability controls or from a project's Scheduled recipes surface. A recipe installation owns the saved prompt, configuration and trigger; pause, resume, edit or stop the schedule there. Project members can see scheduled recipes and their resulting conversations, while only the installation owner can manage the schedule or supply personal connector credentials.

Each occurrence runs through the existing recipe task path and produces an attributable conversation. The conversation is a result and history surface, not the repeatable definition, so conversation lists do not offer an independent schedule action. Use recipe configuration or project Sources when future runs need durable context instead of implicitly replaying a conversation. Read [ADR 0052](architecture/decisions/0052-keep-repeatable-scheduling-in-recipes.md) for the ownership decision.

## Understand Project Workbench

**Project Workbench** is the responsive presentation for coding-enabled project conversations in Work. It is not a third mode or a separate execution environment. It keeps the existing conversation as the durable entry point and presents its sandbox work through Conversation, Activity, Changes, Files and Proof, with Preview available contextually for declared network services.

Conversation always remains available. Activity combines the conversation's existing agent trace with the selected run's recorded plans, model and tool activity, commands, approvals, instructions, validation, errors and outcome. Command output is collapsed into its command, and cost or latency details stay behind an explanation. The view uses recorded summaries rather than hidden model reasoning, redacts recognisable credentials and restores the same order after refresh.

The run status strip lets its runner add an instruction, request continuation, pause at the next safe boundary, resume, cancel or resolve a pending command approval. Submitted instructions move through accepted, queued and processed presentation states and remain visible after reload. Stale actions, terminal runs and expired or already-resolved approvals fail explicitly rather than silently replacing newer state; project members who did not start the run can review it without inheriting its controls.

Changes and Files identify available run evidence without treating it as project Sources. Proof shows the run's recorded objective and outcome, repository revision, changed files, validation and quality-gate result, delivery references, private artefacts, usage, residual risks and incomplete work. It remains truthful after reload: a failed or cancelled run cannot appear successful because optional evidence is absent. Wide web keeps Conversation beside one supporting pane, while narrow web opens the same panes in a full-height panel. iOS may present a compact native summary while consuming the same manifest.

Large logs and diffs stay in private Outputs rather than travelling inside the conversation record. Proof links to them through the existing authorised Output path, so project access still comes from membership and does not expose storage locations or grant execution authority.

Changes presents a searchable changed-file list and syntax-aware unified diff, ordered with contracts and configuration before consumers and tests. Diff sections can be collapsed, and large, binary or unavailable evidence is called out instead of being rendered without limits. Files keeps the recorded changed-file list beside private run artefacts; it fetches a bounded preview only when you choose an artefact.

A coding environment on the project enables new sandbox runs. Without one, a new project conversation behaves like ordinary Work and retains project instructions, capabilities and Sources without disabled coding panes. Removing configuration stops new coding runs but does not hide evidence from runs already attached to a conversation.

Choose a delivery policy when connecting the coding repository. New environments recommend a review branch and pull request; you can instead leave changes uncommitted, prepare only a review branch, target an existing non-protected branch or supply local custom preparation instructions. Existing commit preferences migrate conservatively and remain editable or removable from project settings.

Remote delivery happens only after validation and a separate approval from the person who started the run. The approval shows the repository, intended action, source and target branches, commit and validation result. Polychat checks that person's current GitHub installation and repository access again at execution; it refuses direct delivery to `main`, the default branch or a protected branch. A failed quality gate does not write to GitHub, while partial delivery failures remain visible in Activity and Proof.

Environment setup is optional and removable. Configure it in project settings or select the repository-owned `.polychat/environment.json` convention. A definition can declare full setup commands, lighter resume commands, required runtimes and package manager, and a setup timeout. Enter one command per line; commands containing inline credentials are rejected, and network or risky commands still follow the run's approval policy.

Each run snapshots project-owned setup or reads repository-owned setup from the cloned revision. Activity shows bounded, redacted setup output and whether setup or resume completed or failed. Proof shows the source and exact configuration revision, requirements, duration and terminal status, so a later configuration edit cannot rewrite what an earlier run used.

After a successful full setup, Polychat can save a private environment snapshot. A later run by the same project member reuses it only when the project, GitHub installation, repository revision, lockfiles, setup definition and platform version still match, then applies the lighter resume commands. Activity and Proof say whether the run created, reused or missed a snapshot and show its age and setup provenance.

Project owners and administrators can delete the snapshot or request a rebuild from coding settings. Both actions invalidate reuse immediately; rebuild performs clean setup on the next coding run. A missing, expired or failed snapshot falls back to clean setup, and changing the repository or setup definition also invalidates the previous snapshot.

The same environment definition can declare run-scoped services such as a web application, supporting API or watcher. Give each service a name, repository-relative directory, command, dependencies, optional declared port and health check, startup timeout and bounded restart policy. Polychat validates the graph and ports inside the sandbox, starts dependencies first and refuses to attach a declaration to a port that is already occupied.

The workbench Activity pane shows current service health above its ordered lifecycle and bounded redacted logs. The person who started the run can start, restart or stop a declared service without gaining a general terminal; restarting a dependency also restarts dependants that were active. Proof records the service outcomes and restart counts, while container addresses, process IDs and undeclared ports remain unavailable. Services stop with the run and do not create persistent project daemons.

A healthy service with a declared port can receive a short-lived preview. Polychat opens it on an isolated, opaque origin after checking current project membership, run state, service health and the exact declared port. Access expires after five minutes and ends sooner when you revoke it, the run finishes, the service stops or your project membership no longer permits the request. Refresh creates new access rather than extending stale authority.

Preview content is the project's untrusted application, not part of Polychat's controls. The gateway does not pass Polychat credentials or the preview application's cookies to the service, blocks external redirects and broad embedding, and never reveals the container address or private forwarding token. Opening a preview grants no runner controls, connector credentials, command approval or agent-driven browser control.

The Preview pane keeps trusted route, viewport, refresh, external-open and review controls outside the application frame. You can mark a normalised screen region or write a safe element reference, add a bounded annotation and send it as an ordinary instruction to the same live run. Only its initiating runner can submit that instruction; the recorded Activity identifies the submitting user. Polychat does not inspect the preview DOM, store a screenshot or let application content invoke these controls, and stale access must be replaced before more review.

Project membership grants project access, not somebody else's execution authority. The runner must have current sandbox and repository authority; connector credentials stay personal; approvals remain separate, exact actions. Read [ADR 0043](architecture/decisions/0043-project-workbench-presentation.md) for the presentation boundary, [ADR 0045](architecture/decisions/0045-require-explicit-sandbox-delivery-policy.md) for delivery, [ADR 0046](architecture/decisions/0046-version-sandbox-environment-preparation.md) for setup and resume, [ADR 0047](architecture/decisions/0047-scope-and-invalidate-sandbox-environment-snapshots.md) for environment caching, [ADR 0048](architecture/decisions/0048-supervise-declared-project-services.md) for run-scoped services, [ADR 0049](architecture/decisions/0049-gate-sandbox-previews-through-current-project-authority.md) for preview authority, and [architecture context](architecture/context.md#project-workbench-boundary) for ownership and implementation seams.

iOS can notify you when project work needs input or approval, is ready to review, completes or stops. Lock-screen text stays deliberately generic; opening it reloads the exact conversation, task or run through your current membership. The compact run view shows Activity and terminal Proof, lets the initiating runner approve or reject a pending request, add an instruction, continue or cancel, and summarises changed files without becoming a mobile IDE. A revoked membership, expired approval or run that finished before you opened the alert shows current server state instead of replaying the notification. Read [ADR 0053](architecture/decisions/0053-deliver-mobile-work-notifications-without-moving-authority.md) for the mobile boundary.
