# Understand Polychat

Polychat combines personal **Chat** with collaborative **Work**. Start with the web app and API; add sandbox coding, training or native iOS only when needed.

Chat is conversation-first, with personal capabilities and rich experiences below `/chat`. Work organises projects inside workspaces, with shared conversations, instructions, sources, outputs and selected capabilities. Work access requires the appropriate plan and current workspace membership. There is no third global Apps or Recipes mode.

## Choose how work runs

- Use a conversation for interactive work, an experience for a richer workflow, a recipe for reusable configured work, and a project task/flow for durable agent execution and hand-offs.
- Configure skills and saved agents in the capability library. Skills supply instructions; agents supply personas and capability requests. Their runner still needs access to everything they use.
- Keep connector installations and credentials attributable to the person running the work. Project membership does not grant another member's external account.
- Use the project's **Automatic model preference** for its default routing tier. Explicit request tiers or models override it; it is not a spending cap.
- Treat **sources** as durable inputs and **outputs** as durable results. Project scope adds collaboration; conversation links add provenance.
- Show durable output origin from its captured run, effective model/provider, skill revisions, source references and approval outcomes. Label incomplete history as partial or legacy, and never treat an old reference as current access.
- Compare output revisions before restoring supported local text results. Restore appends a revision and preserves provenance; files, connector or publication effects, provider jobs and sandbox repository changes are review-only and need their own external compensation.

For models that support it, the **Processing** selector offers Automatic, Standard and Fast with catalogue pricing. Changing the model clears an explicit choice; web Chat, Work and iOS use the same contract.

Model and capability readiness is a short-lived preflight, not an execution guarantee. Ready, setup-required, unavailable and unknown checks remain distinct and show the next useful action. Removing an account or provider key does not silently replace the selected model: web and iPhone retain it, block sending and ask you to refresh access or choose another model. The server checks current authority again when work starts.

Changing models affects the next run and keeps compatible attachments and the conversation's stored history, but resets model-specific response settings. Finish or cancel an active run, approval or question first. Remove incompatible attachments before switching; start a new conversation for a one-turn image model when the current conversation already has history. Use a branch or second opinion for comparisons so each result keeps its own model attribution and usage identity.

## Find conversations and results

Conversation lists can group ordinary chats and task conversations. In a saved remote conversation, **Branches** opens related threads without copying history. Personal branches remain owner-scoped; project branches remain within the same membership-authorised project. Local-only and iOS navigation do not gain this web branch browser.

Each accepted stored task has one run identity and an authoritative state that is separate from the conversation and its visible assistant messages. Web and iOS preserve that identity, while repeated submissions are only safely deduplicated when they reuse the same command identity. Queue-dispatched project tasks continue independently of the request that starts them. Personal stored Chat remains best-effort after a connection loss, and local-only Chat remains private to the device with no server recovery.

An interrupted connection recovers the same accepted task, including saved tool and partial assistant messages, and keeps observing it until attention or completion is reported. Web and iPhone consume ordered task updates and automatically replace local state with an authoritative snapshot if updates were missed or retained history expired. Repeated or late delivery cannot duplicate visible work or reopen a finished task. Stop targets that task and attempt on either client. A stop request appears before execution has actually stopped, and a tool or provider call already in progress may finish before cancellation becomes final; changing views and stopping voice recording are separate actions. Questions, tool approvals and stage reviews have distinct durable controls rather than being inferred from assistant prose. On iPhone, project-task cards support structured choices, written answers and exact approve or reject actions. They show sending, retryable failure, expiry, resolution on another device and a saved decision whose provider continuation was interrupted. Project-task questions and approvals remain recoverable for seven days; recovery expires older unresolved interactions instead of leaving a dead control. Both clients defer to persisted interaction state, and current workspace membership is checked again for every response.

Project task detail on web and iPhone also shows a durable activity timeline after reopening or switching devices. Proposed outcomes are separate from actual runs, steps, tool lifecycle, questions or approvals and results. Waiting, tool failure, interruption, cancellation and completion remain distinct, while raw tool payloads and private reasoning stay out of the timeline. Web can expand safe summaries; iPhone keeps actionable and terminal entries in its compact view even when the conversation contains long generated text.

A project task keeps the saved flow it started with and shows each stage as proposed, executing, completed, failed, interrupted or abandoned from actual run evidence. Open a stage to reach its exact run conversation or durable result; retries appear as separate attempts with their own provenance. You can edit an untouched pending plan, but cancelling after execution keeps completed evidence and requires a new task for changed work. Polychat retries a failed model-only stage at its existing boundary, but asks you to reconcile an external provider when an approved write may already have happened.

The task inbox on web and iPhone surfaces pending decisions, meaningful failures, assignments and recent useful completions. Read and dismiss affect only your inbox, never the task, and the server checks current membership and task state whenever it lists or opens an item. Notification permission and Polychat registration are separate states: granting browser or iPhone permission does not prove delivery is configured. Preferences apply per account, registrations per installation, and signing out removes only that installation. Push messages use generic copy and resolve to current task state, so an old notification cannot reveal stale detail or restore a finished action.

Stored conversations compact older history when requested or when model context pressure requires it. A snapshot archives only the complete messages supplied to its summary input; messages beyond that bounded input, including an individually oversized message, remain active. Web and iOS compaction status shows how many candidate messages were summarised or preserved verbatim and how many remained active.

Each later model step checks context pressure again. Large tool results are shortened only in the model prompt and remain stored for authorised retrieval; further pressure removes older complete steps before the latest user constraint. Stored-run context views on web and iPhone show attached sources, effective skills, the active summary, omissions and context-window usage. Usage says whether it came from the provider or is an estimate, and omitted text is never described as fully retained. Removing a composer attachment changes the next submitted turn; changing curated project context affects later new project conversations rather than rewriting an existing conversation.

Temporary model rate limits, timeouts, network failures and provider outages can trigger one visible repeat of that model call, with no more than two repeats across a run. Web and iPhone show whether the run is waiting or trying again, and stopping during the wait prevents another attempt. Invalid input, credentials, permissions, policy, conflicts and usage limits do not retry. If an external write loses its response, Polychat reports that it may have completed: explicitly idempotent operations can repeat once with the same parameters, while other writes require you to check the external system first.

Usage is charged to the runner in monthly credits. A stored run shows its reserved estimate separately from recorded consumption and settlement, across all retry attempts. A reservation is not a charge; missing provider usage appears as unknown rather than zero. Workspace owners and administrators can review attributed spend without creating a shared allowance. Read [usage](operations/loop-cost-controls.md) for enforcement and reporting, or [architecture context](architecture/context.md) for the implementation map.
