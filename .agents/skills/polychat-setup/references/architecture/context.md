# Architecture context

Use this map to locate current responsibilities. Read the relevant [ADR](decisions.md) for rationale; provider lifecycle 0038 and governance 0040 are accepted designs awaiting implementation, not current API guarantees.

## Vocabulary

| Term                           | Meaning                                                                                                                                             |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chat / Work                    | Personal conversation and collaborative workspace modes sharing one conversation runtime.                                                           |
| Workspace                      | Membership and role boundary for collaborative work. Work requires its account entitlement as well as membership.                                   |
| Project                        | Shared instructions, conversations, context, capabilities and tasks inside a workspace.                                                             |
| Capability                     | An app, recipe, skill, connector, agent or tool. Configuration, enablement and authorisation are distinct.                                          |
| Experience / app               | A rich workflow from `/capabilities`; an experience with an owning capability is presented as an app. `apps/*` instead means deployable workspaces. |
| Scope                          | Personal or project ownership passed to shared components and services. Agents additionally support workspace ownership.                            |
| Source / output                | Durable input / result. A project ID makes the resource collaborative; a conversation link adds provenance.                                         |
| Provider connection            | A person's external authority. Work does not inherit another member's credentials.                                                                  |
| Skill / agent                  | Loadable instructions / a saved persona with capability requests. Neither grants execution permission.                                              |
| Task / flow                    | Durable project work with its own conversation and goal / ordered execution stages. Distinct from the internal `tasks` queue.                       |
| Attention / inbox              | Current task state needing a person's awareness / its per-person read and dismissal projection. Neither grants task authority.                      |
| Activity / audit               | User-visible execution history / immutable workspace governance history retained after deletion.                                                    |
| Credit / reserve / reservation | Metered allowance / plan grace beyond the allowance / held estimate for work not yet settled.                                                       |

## Conversation execution

`lib/chat/core` orchestrates requests. `validation` and `preparation` establish model, scope and prompt state; `agent` runs the shared loop; `messages`, `streaming`, `tools` and `policy` own their named responsibilities. Keep feature internals out of the top-level orchestrator.

Both streamed and buffered turns use common finalisation and goal policy. Turn completion owns persistence, connector cleanup and lock release. Every authenticated stored execution receives a persisted `run_<id>` and versioned command receipt independent of its conversation, messages, model steps and tool calls. Runs move through accepted, running, waiting, cancelling and immutable terminal states; attempt-fenced transitions prevent stale completion. Conversation detail exposes `latest_run`, messages and project tasks may reference it, and authorised status reads use personal ownership or current project membership. Older clients may omit command and run IDs, but only explicit command IDs make retries idempotent. See [ADR 0042](decisions/0042-persist-chat-run-identity.md) and [ADR 0043](decisions/0043-order-chat-run-events-with-snapshot-reset.md).

Disconnection detaches SSE; it does not finish the run. Web and iOS resolve a lost receipt from the submitted command, anchor an authorised exact-run snapshot, then poll ordered events after that snapshot’s cursor every two seconds. Lifecycle writes and message references share the run’s monotonic sequence and a bounded 500-event retained window. A retention gap, invalid cursor, oversized stream event or non-contiguous page explicitly replaces client state with an authoritative snapshot; duplicates, stale attempts and terminal regressions are ignored, while unknown or newer protocol events fall back to snapshots. Cancellation names the run and observed attempt, is idempotent per command, and distinguishes `cancelling` from owner-confirmed `cancelled`; stale attempts cannot stop a successor. The owner checks cancellation between model and tool safe points, so an in-flight external effect is allowed to settle before the run stops. Interactive stored Chat remains best-effort Worker continuation and local-only Chat remains device-private.

Queue-dispatched stored project tasks are the durable execution cohort. The queue task holds a renewable persisted owner lease, and both task settlement and project-task state commits compare that owner. Redelivery reconciles persisted success or a waiting interaction, but marks mid-run owner loss interrupted rather than replaying model or tool work. Waiting interactions are recoverable for seven days. Run-keyed credit reservations and connector cleanup records let a successor settle resources after owner loss.

Authorised project-task detail projects the latest current-run question or approval as protocol version 1 interaction state. Its stable envelope retains structured prompts, options, written-answer support, exact tool approval context and acknowledged outcomes; `pending`, `resolved`, `expired` and `interrupted` remain distinct. Web and iOS submit through the existing exact-task endpoints, which recheck current membership and the pending interaction under the conversation lease. Native submission state is local and temporary, while task detail remains authoritative. Streamed iOS tool-result parts retain raw structured data instead of reducing interaction payloads to display strings. See [ADR 0044](decisions/0044-project-native-task-interactions.md).

The same task-detail read exposes a newest-first protocol version 1 activity projection reconstructed from project-and-task-scoped runs, bounded run events, run-keyed message parts, goal progress, interactions and completions. Proposed outcomes remain visibly distinct from actual execution; run snapshots cover legacy or trimmed journals. The shared presentation contract carries safe summaries and open event types, not reasoning, tool arguments or raw tool results. Web owns expandable detail in `component-workspaces`; iOS keeps a compact summary above the transcript and validates task scope before replacement. See [ADR 0045](decisions/0045-reconstruct-project-task-activity.md).

Task attention is a versioned projection of current authoritative task state, not a second task lifecycle. Pending decisions and meaningful failures are visible to current workspace members, assignments to the current assignee, and completions for 30 days to the creator or assignee while they remain members. Per-person read and dismissal receipts are keyed by task attention version and never mutate task state or execution authority. Web and iOS resolve notification links through the server before opening current task detail, so membership removal, later transitions and old deliveries become harmless stale links.

Notification preferences, device registrations and delivery outbox records have separate ownership. A registration belongs to one user, platform and installation; replacing a push token or browser subscription updates that installation while an endpoint fingerprint prevents cross-account reuse. Destinations are authenticated-encrypted with `PRIVATE_KEY`, and only the fingerprint is indexed. The outbox deduplicates each registration and task version, then rechecks membership, current attention state, preference and registration immediately before delivery. Provider payloads contain generic copy plus current identifiers and a server-resolved path, never task detail, tool arguments or private reasoning. See [ADR 0049](decisions/0049-project-current-attention-and-notification-delivery.md).

`services/conversations/coordinator/client.ts` serialises history mutations at their entry points. The lock is non-reentrant and uses an opaque owner token, a five-minute lease and one-minute renewal. Only the current token can renew, pass a write fence or release; absent or unreachable coordination refuses mutations, while an abandoned lease becomes available after expiry. `lib/conversation/write-fence.ts` is the persistence-boundary contract reused by the conversation manager. Tool-result compaction removes JSON formatting whitespace before provider calls without changing values, protocol fields or stored history; it has no settings or saved policy. `lib/session` owns history compaction: a snapshot records the exact message IDs fully represented within its bounded summary input, and one D1 batch inserts the snapshot and marker, archives only that covered prefix, and refreshes conversation metadata. Later candidates, non-text messages and individually oversized messages remain active; provider failure stores the covered input as a verbatim fallback transcript. Display-only compaction and goal markers stay out of model input. Async provider jobs use `lib/async` and polling handlers, with terminal writes taking the same lock.

Before every model step, `lib/chat/policy/context-budget.ts` reserves requested output capacity or 15% of the current model window, preserves system/developer instructions and the latest user-controlled message, and then fits the active summary and newest complete assistant/tool units. Provider copies of tool results above 6,000 characters use bounded head-and-tail excerpts; stored messages remain unchanged and authorised message reads retain the full result while retention permits. The exact run attempt stores a protocol version 1 context snapshot with included and omitted counts, source and approval references, effective model/provider and skills, active summary and reported-or-estimated input usage. Resuming a waiting run clears its prior snapshot. Web and iOS present the same optional contract; local-only chat remains device-private and receives no server run snapshot. See [ADR 0046](decisions/0046-budget-and-report-run-context.md).

Durable outputs snapshot bounded protocol version 1 provenance: origin, producing run and attempt, effective model/provider, loaded skill revisions, source references and approval outcomes. Content revisions copy that immutable snapshot. Authorised detail retrieval resolves each source against current authority and reports unavailable references without a link; output lists and public shares omit provenance. Legacy rows remain explicitly legacy, and producers with incomplete execution facts record partial provenance. See [ADR 0050](decisions/0050-snapshot-effective-provenance-on-durable-results.md).

Output history is append-only. A supported restore copies an earlier title and structured content into a new revision while preserving current status, sensitivity and provenance, recording its actor, parent and restored-from lineage, and atomically auditing project restores. Expected-revision fencing and current membership protect concurrent and project writes. Only article analysis/report/summary, notes and Strudel patterns are reversible; files, provider jobs, connectors, publications and sandbox repository effects remain comparable but review-only because a local row cannot compensate their external effects. See [ADR 0051](decisions/0051-append-safe-local-output-restores.md).

Each project task is a stable plan and snapshots its selected saved flow before execution. Accepted runs persist the exact flow-stage ID; completions and outputs retain the producing run, attempt and provenance. Authorised task detail projects stage state only from those records, so unexecuted stages remain proposed and interrupted attempts remain distinct from later successful attempts. Dispatch failures and model-only failures can resume at the same snapshot boundary, while a consumed external-operation approval requires reconciliation instead of a blind retry. Plan inputs are editable only before execution, and executed plans cannot be reopened or deleted. Older tasks without stage identity use an explicit unattributed task stage rather than a current-flow guess. See [ADR 0052](decisions/0052-snapshot-project-flows-and-derive-stage-evidence.md).

`lib/chat/policy/provider-retry.ts` owns model retry classification, delay and run-wide attempt accounting. Provider and gateway calls make one network attempt; the turn boundary permits one repeat per eligible call and at most two repeats across a run. Retry state is attempt-fenced, persisted and ordered for web and iOS. Cancellation interrupts the wait, while a failure after streaming begins remains terminal. Connector execution classifies a post-invocation write failure as definitively not applied or unknown: only a definitive rejection or an explicitly idempotent unknown outcome may repeat once with identical parameters. A non-idempotent unknown outcome requires external reconciliation. See [ADR 0047](decisions/0047-bound-model-retries-and-surface-unknown-writes.md).

Model and capability catalogue responses carry short-lived, versioned readiness facts with distinct ready, setup, unavailable and unknown states. They explain likely account, plan, credential and policy blockers but never authorise execution; model selection and capability execution re-check current server authority. Web and iOS preserve an invalid saved selection instead of substituting another model. A model change targets the next run, retains compatible attachments and stored conversation history, and clears model-specific response settings. Active runs and their approvals or questions block a change, incompatible attachments must be removed, and one-turn image generation with existing history requires a new conversation. Branches and multi-model responses remain the comparison mechanisms so alternatives keep separate model, run and usage identity. See [ADR 0048](decisions/0048-expire-readiness-and-make-model-handoffs-explicit.md).

Managed tool selection starts small and activates eligible tools after discovery or skill loading. Project grants constrain that activation. Saved agents layer personas into the generated prompt and request tools/skills within the runner's scope. Project tasks use the same engine, with exact dispatch and run identity plus durable question, approval and stage-completion records.

## Data and authority

Authorise project reads and conversations through current workspace membership; apply each resource's management roles separately. Keep private files behind Source/Output access and resolve their bytes server-side before provider calls. Project context is curated explicitly, and built-in memories are owned by the memory service.

Authored skills use D1 identity and stable/draft pointers with immutable private R2 bundles. Pin one stable revision per request while revalidating access on each load. Retrieval similarly uses provider matches only as candidates: active scoped D1 records authorise content, and immutable vector provenance governs cleanup.

Composio owns configured connector credentials and tool schemas. Polychat owns scoped session handles, exact-action approvals, event mappings and cleanup. A queue record, catalogue match or model-produced argument is never authority by itself.

Credit admission reads persisted plan allowances; missing allowances refuse work. The signed-in ledger records idempotent vendor-unit spend, while anonymous actors use running totals. BYOK model/hosted-tool spend is uncharged; other metered work is not. Stored run usage groups ledger events by stable run and attempt, but keeps the admission reservation, recorded consumption and settlement distinct. Missing provider telemetry is unknown rather than zero actual consumption. The assistant-turn finaliser normally settles the hold; cancellation, failure, owner recovery and the 24-hour expiry sweep release unfinished holds through the same idempotent boundary. Workspace reporting is attribution, not a shared balance. See [usage operations](../operations/loop-cost-controls.md) and [ADR 0053](decisions/0053-attribute-run-usage-and-settle-reservations-once.md).

## Web boundaries

`apps/app/src/lib/api/fetch-wrapper.ts` owns credentials, CSRF, timeouts and API error handling. React Query hooks own remote/local coordination and invalidation; the authenticated store owns hydrated user/settings state. `lib/local/local-chat-service.ts` owns local conversation persistence.

Keep customisation drafts in `component-account` as field-level edits over hydrated settings. Refresh untouched controls as settings arrive, preserve local edits until the server returns matching values, and discard drafts when the settings identity changes.

Chat and Work compose the same `ConversationThread` and scoped capability surfaces. Keep backend catalogue metadata authoritative and project request metadata intact. Automatic routing admits text-response chat models, excluding media generation, realtime and specialist extraction models; multimodal chat inputs remain eligible. Failed AI prompt analysis falls back to keyword requirements before scoring eligible models. Host controllers supply resolved links and actions to render packages through their existing providers.

Use shared UI primitives for buttons, dialogs, focus, overlays and reduced motion. Tool messages and parts share `ToolResultView`; declared renderers and payload shape choose the body. Presentation components emit typed, optionally asynchronous intents and only show local acknowledgement after the host action succeeds; persisted interaction state remains authoritative. Native task cards support structured question choices, written answers and exact approve/reject actions. Unknown interaction types stay visible but non-actionable. The stable task destination is `(workspaceId, projectId, taskId, conversationId?)`; inbox and push links resolve that destination against current state and access rather than treating a message as authority. Task activity uses the same project, task and run identities, with an open type plus stable category/status presentation fields that later context, retry, attention, evidence, usage and performance work can extend. Stream rendering coalesces supersedable text, yields after bounded progress batches and flushes before authoritative boundaries. Conversation detail loads the newest 100 visible messages and pages backwards under the same access check; stored output stays complete while text, JSON and table renderers start with expandable bounds. See [streaming operations](../operations/streaming-responsiveness.md) and [ADR 0054](decisions/0054-bound-live-streams-and-page-durable-history.md).
