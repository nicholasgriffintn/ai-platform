# Polychat Architecture Context

Polychat is a multi-model assistant platform. It combines hosted chat, agents, retrieval, generated media, realtime sessions, workflow-style apps, metrics, training control, and sandboxed coding runs in one monorepo.

Use this reference as the domain context for architecture reviews and Polychat setup decisions. Keep new terms here when they become load-bearing concepts, and use the architecture vocabulary of module, interface, seam, adapter, depth, leverage, and locality when proposing changes.

## Product Terms

- **Product mode**: the top-level Chat or Work context. Chat is a personal, conversation-first surface; Work is a signed-in Pro, workspace-first surface. Switching modes changes navigation and information architecture, not the underlying provider runtime. Authentication and the Pro entitlement are enforced by both the interface and the workspace access seam.
- **Workspace**: the durable sharing and authorisation boundary for collaborative work. A workspace contains members and projects; users discover only workspaces where they hold a membership.
- **Workspace membership**: the connection between a user and a workspace, with an `owner`, `admin`, or `member` role. Membership grants access to every active project and project conversation in that workspace; role checks separately protect management operations.
- **Workspace invitation**: an email-bound, expiring, single-use offer of `admin` or `member` membership. Only a token hash is persisted; acceptance requires an authenticated user with the invited email address.
- **Project**: the outcome-oriented work unit inside a workspace. A project owns shared instructions, project conversations, and a curated capability library, and inherits its access boundary from the parent workspace.
- **Project coding environment**: an optional project configuration that binds project conversations to an authorised Git repository and sandbox execution settings. The coding task is selected per conversation; it is not project configuration or a product mode.
- **Project capability**: an app, recipe, skill, tool, or agent selected for a project. An attached agent keeps its persona but not its tool authority: its `enabled_tools` are intersected with the project's effective tools, and only someone who can read it may attach it (ADR 0029). App and recipe associations are visible to every project member but remain manageable only by the member who attached them; project tools remain administrator-managed. The association organises reusable assistant runtimes around project context rather than exposing apps and recipes as global product destinations. Runtime-owned settings stay with their owning API; recipe configuration, for example, remains attached to a user-owned recipe installation rather than being copied into the project association.
- **Default project tool**: a model tool published by `/capabilities` and available to every project without a stored association. Tools marked `requiresConfiguration` remain visible but inactive until an administrator stores valid project configuration; the backend resolves that configuration into provider `tool_options` and never trusts request-supplied replacements in project chat.
- **Capability configuration**: validated runtime settings for a capability in an explicit user or project scope. `capability_configuration` keys settings by scope, capability kind, and capability ID without implying enablement or authorisation. Personal and project model-tool adapters resolve these settings into provider `tool_options` only when the tool is selected.
- **Project experience**: a rich Work surface for an enabled project capability whose workflow needs more space than chat or a single form. Experiences live below the project, reuse existing app runtimes and Polychat components, and persist their results as project-scoped outputs.
- **Conversation**: the durable thread identified by a completion ID. Its persisted type is `chat` for an ordinary person-led conversation or `task` for agent work created by a project task or recipe. Type describes the thread's product purpose; it does not create a second runtime or alter authorisation. Conversations may be remote, local-only, shared, branched, parented to another conversation, or attached to a project. Branches inherit the parent type. `conversation.user_id` records the creator; it is not the sole authorisation rule for project conversations.
- **Message**: a normalised chat item with role, content or parts, optional reasoning, citations, tool calls, usage, model metadata, and generated artefact data.
- **Conversation compaction**: the process of summarising older active conversation history into a hidden snapshot while leaving archived history visible to the user. Compaction status rows are display-only messages and must not be sent to provider adapters.
- **Conversation mode**: metadata that changes how a conversation behaves, such as ordinary chat, live sessions, recipe, or focused app workflow. Background work is not a mode: every turn outlives its connection, so there is nothing left for a mode to opt into. Behaviour that only needs different instructions belongs in a skill the model loads, not in a mode. Project coding execution is a project capability, not a conversation mode.
- **Model**: a generation target from the model catalogue. A visible model may be shown for the current provider configuration; an executable model is also active and allowed by the person's Free, Pro, or BYOK access. The server validates explicit choices and resolves automatic defaults from the executable set. `/models` exposes those decisions as `isExecutable` and `isDefault`; clients repair persisted non-executable selections, consume the default, or request automatic routing.
- **Model maker**: the organisation behind a model, declared in `packages/schemas/src/model-makers.ts` and derived from the model family first, its runtime provider second. A maker spans providers, so Claude served by OpenRouter still resolves to Anthropic. Makers are a display and preference grouping, not a routing or authorisation seam.
- **Model benchmark cache**: persisted third-party benchmark, pricing, and performance data used to inform model routing and catalogue decisions without exposing upstream API keys to clients.
- **Provider capability**: a backend capability category such as chat, audio, speech, transcription, image, video, music, embedding, search, research, guardrails, realtime, messaging, or training.
- **Provider adapter**: a concrete backend implementation for a provider capability. Provider selection is a real seam because capabilities have multiple adapters.
- **Realtime provider catalogue**: the registry-derived public view of registered realtime adapters. Each adapter owns its typed descriptor and private configuration requirements; the API adds current model access and readiness without exposing secrets. The browser enriches that response with protocol behaviour and keeps one non-ready initial-render fallback, never a competing provider authority.
- **Agent**: a configured assistant persona with optional tools, MCP servers, team role, model settings, and sharing metadata.
- **Tool**: a callable assistant function exposed through the backend, including retrieval, media, code, workflow, and delegation tools.
- **Experience**: a rich frontend workflow published by `/capabilities` from the curated catalogue in `apps/api/src/services/experiences/config.ts`. An experience that declares a `capabilityId` is also the thing a project or person enables, and is presented as an app; experiences without one are always available.
- **Runnable tool**: a function tool a person can run from the interface rather than waiting for a model to call it. `/tools/:id` derives its form from the tool's own input schema and `/tools/:id/execute` stores the result as an output. Function tools are never published as apps.
- **Capability scope**: whether capabilities are curated for a project or simply available to a person. A `CapabilitySurface` carries a base path and an optional project ID so one set of frontend components serves both, and `requiresExplicitEnablement` distinguishes a project, which attaches capabilities deliberately, from a person, who already has them.
- **Assistant capability**: a product-level capability discovered through project libraries and chat composer surfaces, backed by app, recipe, skill, connector, agent, or tool catalogues. Capabilities publish availability, auth state, read/write risk, approval policy, required model capabilities, required connector state, launch method, execution mode, saved-state support, availability reason, and tags while keeping their runtime-specific implementation separate.
- **Skill**: a portable [Agent Skills](https://agentskills.io/specification) directory whose `SKILL.md` contains a name, triggering description, and specialised instructions the model loads on demand instead of carrying in every prompt. The system prompt lists only each ready skill's name and description; `load_skill` returns the body and relative resource paths, or one exact resource. Built-in skill data lives under `apps/api/src/data-model/skills` and is imported directly into the Worker. A user-authored skill has a D1 identity and mutable draft/stable pointers, while every complete `SKILL.md` and resource bundle is an immutable private R2 revision. Product-specific presentation and requirements use reserved namespaced frontmatter metadata. Skills are a capability kind in both scopes. Always-on skills, such as `recipes`, are part of the product contract and cannot be turned off. Skills own behaviour the model performs by following instructions; a function tool is reserved for capability the model cannot reach by reasoning alone (ADR 0021).
- **Capability discovery**: the read-only, model-callable search across tools, recipes, and connectors. Results distinguish ready, setup-required, and unavailable capabilities, and may mark an eligible native tool for response-scoped activation without persisting enablement. They carry only stable setup references rather than connector, recipe, or configuration authority. Personal Chat uses the person's catalogue; Work is restricted to the effective project capability boundary and the current member's installations and connections.
- **Artefact**: generated output rendered beside or inside conversation UI, including code, HTML, SVG, image, and combined artefact views. Artefact guidance lives in the `artifacts` skill rather than the system prompt, and availability follows tool support rather than a per-model flag.
- **Output**: a durable result produced by a person or assistant capability. Outputs are personally owned unless assigned to a project, may be linked to a conversation or parent output, retain revisions, and use revocable hashed-token shares.
- **Source**: durable input material such as a file, memory, text, URL, connected record, or repository. Sources use the same personal-or-project scope as outputs and may be organised into collections.
- **Memory**: retrieval context represented by a source with kind `memory`. The shared memory manager owns classification, deduplication, retrieval, provider indexing, and source persistence for both personal and project scopes; generic source creation cannot manufacture memory records.
- **Project context**: the reserved project source collection whose available sources are attached to every project conversation alongside project memories. Owners and administrators curate the collection; all project members consume it through the shared conversation runtime.
- **Project recipe installation**: a user-owned recipe configuration and trigger set attached to a project. Project members may see installations and their schedules, but only the creator may change them. Connector authority remains in that creator's provider connections, and scheduled execution retains both the user and project scope.
- **Provider connection**: user-owned authority for an external provider account. Bespoke connectors encrypt credentials in Polychat; migrated recipe connectors keep credentials and connected-account state in Composio. Connections are referenced by sources and capability runtimes but are never promoted to workspace-owned credentials implicitly.
- **Connector run**: one server-generated execution boundary for connector discovery and operation calls. A Composio run stores an opaque local session handle bound to the user, completion, recipe installation, provider, auth config, selected connected account, and exact operation allowlist; clients never receive or supply the upstream session ID.
- **Connector operation approval**: a provider-neutral, short-lived, one-use receipt for one exact external action stored at an authenticated conversation and tool-call boundary. The connector adapter declares whether it supports stored-action approval. The server replays that stored call without trusting client input, after revalidating the user, connector run, completion, provider, operation, argument digest, adapter authority, account, recipe, installation, and project scope. It executes the action once, persists its terminal result, then lets the model summarise with tools disabled. Conversation reads project the receipt's authoritative pending, approved, rejected, consumed, or expired state onto the approval message so reloaded clients cannot restore stale controls. A duplicate consumed receipt reuses the stored result; a consumed receipt without one fails closed as an indeterminate execution. Scheduled or event-triggered runs cannot perform approval-gated writes.
- **Recipe event trigger**: a user-owned Composio trigger attached to a recipe installation and one explicit connected account. Verified trigger events enqueue idempotent recipe tasks in the installation's user and project scope; event fields remain untrusted input and never become instructions.
- **Template**: reusable personal or workspace configuration. Project templates capture project fields and capability configuration and instantiate a project atomically after current catalogue validation.
- **Project task**: the durable unit of agent work in Work. It carries an objective, acceptance criteria, expected output, context, constraints, dependencies, approval gates, a token budget, and an optional human owner. Each run binds the project task to one exact internal queue dispatch before it becomes claimable. Dependencies gate a start, forbidden tools are withheld, approval gates are unioned onto the turn, and the token budget blocks. A task owns a project conversation and the goal that conversation carries. Every completed stage stores a durable completion snapshot containing its written output, evidence, and approval state. Automatically advancing stages approve their snapshot and hand off; a human-gated stage creates a pending approval state on the task. Its lifecycle is backlog, queued, running, blocked, review, done, or cancelled; `awaiting_input` is a blocked reason backed by the latest unresolved `ask_user` tool result, not inferred prose. Not to be confused with the internal `tasks` queue, which is system-owned background execution, or with a sandbox `task`, which is a prompt string.
- **Runner identity**: the member whose connections, installations, and membership a task run executes with. It is the person who started the run, never the assignee and never the workspace, because connector authority is user-owned.
- **Project flow**: an optional ordered list of stages a project's tasks walk through. A stage names instructions, an agent, zero or more attached skills, a mode, an approval policy, and whether goal completion hands work to the next agent automatically or stops for human acceptance. For a task run, the stage and task `requiresApprovalFor` values are the complete approval policy; the mode still supplies instructions and step budgets but adds no hidden tool denials or approvals. One flow per project, stored on the project and captured by project templates.
- **Attention**: the aggregation of everything across a person's workspaces that has stopped and wants them — pending approvals, stalled or limited runs, tasks in review, and work assigned to them.
- **Activity record**: a user-visible execution projection, including sandbox runs, whose lifecycle is useful in personal or project history.
- **Workspace audit record**: an immutable project/workspace governance event for membership, invitations, projects, capabilities, templates, outputs, sources, and sharing changes. Audit history is retained after a workspace is deleted.
- **Agent trace**: a derived view of model calls, tool calls, tool results, approvals, provider errors, usage, latency, and final synthesis for a conversation.
- **Async invocation**: provider or app work that returns before final output is ready. Messages carry `data.asyncInvocation`, the backend polls through provider handlers, and the frontend refreshes pending conversations until the message completes or fails.
- **Sandbox run**: an automated coding task executed by the sandbox Worker and streamed back as task events.
- **Training job**: a user-scoped model training request submitted through the API Worker and executed by the training Worker.
- **Metrics event**: Analytics Engine data surfaced through the API Worker for operational reporting.

## Workspace Map

- **`apps/app`** is the main React Router frontend. Route files under `src/pages` stay thin and compose feature modules from `src/components`, hooks from `src/hooks`, API clients from `src/lib/api`, domain helpers from `src/lib`, and persisted UI state from `src/state`.
- **`apps/api`** is the Hono backend Worker. `src/index.ts` owns global middleware, OpenAPI docs, route mounting, scheduled events, queue events, and Durable Object export. Route modules validate and orchestrate; non-trivial behaviour belongs in `src/services`, `src/lib`, or `src/repositories`.
- **`apps/sandbox-worker`** is the isolated coding-run Worker. It owns `/execute`, JWT and GitHub-token checks, Cloudflare Sandbox execution, task runner selection, cancellation, and SSE task events.
- **`apps/training`** is the internal training Worker. It owns authenticated job/deployment routes, provider execution, persisted training records, and event history.
- **`apps/mobile`** is the iOS client. It mirrors core conversation, model, auth, streaming, artefact, and tool concepts in Swift.
- **`packages/schemas`** is the shared contract module. It exports Zod schemas and inferred types used by the frontend, backend, sandbox Worker, and training Worker.
- **`packages/library-agent-core`** is the shared agent loop module. It exposes the decision loop, approval resolution, and action handlers used by sandbox-style agent execution.
- **`packages/library-registry`** is the shared categorised-registration module. It exposes `CategoryRegistry` and `RegistryError`; `ProviderRegistry` and `ToolRegistry` are typed facades over it.
- **`packages/component-*`** are the shared React DOM render modules. They accept data, status, permissions, and actions, emit typed product intents, and never import a router, a store, or an API client. `apps/app` keeps the controllers that bind hooks, stores, routes, and analytics to those interfaces.

## Key Seams

- **HTTP route seam**: `apps/api/src/lib/http/routeBuilder.ts` centralises route registration, OpenAPI metadata, Zod validation, auth requirements, and response wrapping. Route modules should call into deeper modules instead of owning business logic.
- **Request context seam**: `apps/api/src/lib/context/serviceContext.ts` provides request-scoped environment access, repositories, database wrapper, request cache, authenticated user checks, user settings, and logging.
- **Persistence seam**: `apps/api/src/repositories` owns D1 access. Repositories should hide SQL, row mapping, and storage errors behind domain-specific methods.
- **Workspace domain seam**: `packages/schemas/src/workspaces.ts`, the workspace and project route modules, `apps/api/src/services/workspaces`, and `WorkspaceRepository` own shared contracts, role policy, invitation lifecycle, project composition, and persistence. Callers must enter collaborative data through this seam rather than inferring access from identifiers supplied by the client. Project conversations inherit this workspace boundary and cannot be published through personal Chat sharing.
- **Workspace access seam**: `apps/api/src/services/workspaces/access.ts` resolves workspace membership and role requirements for workspace and project operations. Owner-only operations include workspace deletion; owners and admins manage workspace details, projects, tools, and invitations. Every member can read project work and may attach an app or recipe, while only the attaching member may update or remove that association.
- **Capability configuration seam**: `CapabilityConfigurationRepository` persists scope-owned runtime settings behind a scope, capability-kind, and capability-ID key. Personal tool services bind the scope to the authenticated user; project services bind it to a membership-authorised project and update configuration atomically with the project association. Configuration must not be treated as capability enablement, ownership, or execution authority.
- **Conversation authorisation seam**: `ConversationManager` treats `conversation.user_id` as creator attribution and delegates project-conversation access to `WorkspaceRepository.canAccessConversation`. Standalone conversations remain creator-scoped; any current member of the parent workspace may read and update a project conversation.
- **Registration seam**: `packages/library-registry` owns categorised registration, alias resolution, and singleton or transient lifecycle caching. `apps/api/src/lib/providers/registry/ProviderRegistry.ts` and `apps/api/src/lib/tools/ToolRegistry.ts` are typed facades that map `RegistryError` codes onto `AssistantError` wording; they must not reimplement storage, aliasing, or lifecycle. New registries should build on the package rather than copy a registry.
- **Retry seam**: `packages/library-client/src/retry.ts` owns `withRetry`, `Retry-After` header parsing, and Polychat rate-limit body parsing. Callers supply their own retryable-status policy and clamps, because the web query predicate and the sandbox Worker request loop classify different statuses. `apps/api` continues to delegate provider retries to AI Gateway request headers rather than this loop.
- **Provider capability seam**: `apps/api/src/lib/providers/library.ts` and `registry/ProviderRegistry.ts` resolve capability adapters lazily by category and provider name. New provider behaviour belongs behind the relevant capability registration.
- **OCR seam**: `packages/schemas/src/ocr.ts` and `ocr-batch.ts` own the synchronous and batch contracts; `apps/api/src/lib/providers/capabilities/ocr` owns Mistral request, normalisation, persistence, and Batch API adapters; and `apps/api/src/services/apps/retrieval/ocr` owns authorised private input resolution and personal or project Output scope. `extract_text_from_document` and `/apps/retrieval/ocr` share the synchronous service. Batch routes store progress in an `ocr_batch` Output, while `OcrBatchPollingHandler` revalidates project access and stores terminal NDJSON as an `ocr_batch_result` child Output. Private file bytes are resolved server-side and must not be placed in polling tasks or exposed as private URLs to Mistral.
- **Recipe connector adapter seam**: Composio's enabled auth configs and current non-deprecated tools generate a compact minified provider/tool index. `apps/api/src/lib/providers/capabilities/connectors/index.ts` builds the fast catalogue and capability guard from that index, while `apps/api/src/services/apps/connectors/connector-adapters.ts` binds provider implementations to execution and stored-action approval capabilities. Shared policy consumes those declared capabilities instead of branching on provider names or authentication types. One stable connector tool creates a user/account/toolkit/auth-config/recipe-scoped Composio Session, discovers current schemas by use case, verifies the returned Session scope, and executes the selected exact tool. Composio actions are not global Polychat functions. There are no provider aliases, argument maps, curated Composio subsets, or same-provider credential fallbacks.
- **Connector approval seam**: `operation-approvals.ts`, `approval-message-state.ts`, `approved-operation-replay.ts`, `connector-run-scope.ts`, `connector-approval-cleanup.ts`, and `ConnectorOperationApprovalRepository` own provider-neutral exact-action receipts, authoritative display state, run scope, retention, and deterministic replay from stored conversation history. `connector-approval-authority.ts` defines the adapter interface; `composio-approval-authority.ts` implements Composio Session, account, recipe, installation, and project validation behind that interface. Pending receipts expire immediately at the end of their execution window; resolved receipts remain for 30 days so conversation reads can restore historical state. Route, tool, model, and UI layers may resolve, present, or summarise approvals but must not reconstruct execution authority.
- **Composio run seam**: `apps/api/src/services/apps/connectors/composio-run.ts`, `ComposioConnectorSessionRepository`, and the chat orchestration finalisers implement the Composio adapter's Session creation, opaque local handles, immutable scope checks, execution, activity correlation, and best-effort deletion. Tool Sessions and hosted credential setup Sessions enter the Composio-specific durable journal because upstream Session IDs, mounts, auth configs, and remote deletion have no shared connector meaning. A scheduled reaper leases expired or cleanup-pending records so a crashed request cannot leave an untracked upstream Session indefinitely. Do not generalise this journal until another adapter has the same lifecycle and can supply a real second implementation.
- **Composio file seam**: `apps/api/src/services/apps/connectors/composio-files.ts` bridges authorised private Source and Output files through the Session `files` mount. It validates resource scope, path, MIME type, size, transfer timeout, and presigned host before upload, and imports explicit mount-file descriptors back as governed Outputs rather than exposing provider URLs. Discovery fails closed for file-taking operations when the private bucket bridge is unavailable.
- **Composio event seam**: recipe trigger services own trigger discovery and lifecycle, while `/webhooks/composio` owns raw-body signature and timestamp verification. A webhook may enqueue work only after its trigger ID, namespaced user, connected account, trigger slug, installation owner, project, and active states match persisted records. The deterministic event task ID provides replay idempotency; event payloads are bounded and labelled as untrusted before recipe execution.
- **Recipe catalogue seam**: `apps/api/src/services/apps/recipes/catalog.ts` is the thin loader for static recipe definitions, derived category/filter exports, and catalogue validation. Add recipe definitions under `apps/api/src/services/apps/recipes/catalog/` by domain group, and keep setup/run prompt construction in `runtime.ts` rather than inside catalogue data files.
- **Project recipe seam**: project recipe installations use `TemplateRepository` with both `project_id` and `created_by_user_id`. Project listing is membership-scoped, mutation is creator-scoped, and connector lookup remains user-scoped. Scheduled tasks carry `projectId` from the installation through invocation and chat completion so generated conversations, instructions, capabilities, memory, and context remain in the project.
- **Pashi tool seam**: `apps/api/src/lib/pashi` owns live Pashi catalogue validation, safe endpoint resolution, tool search metadata, input constraints, and sequential generator/text-converter execution. Assistant function definitions and recipes should use this client instead of constructing Pashi API requests directly; file converters remain outside the chat integration until it owns an explicit upload and async-job lifecycle.
- **Provider hosted-tool seam**: provider utility modules such as `apps/api/src/lib/providers/utils/openaiResponsesTools.ts` own provider-native hosted tool shaping, including MCP, file search, code interpreter, tool search, and other Responses tools. Provider request body modules should compose these builders instead of embedding hosted-tool construction inline.
- **Model analysis seam**: `apps/api/src/services/model-analysis`, `ArtificialAnalysisRepository`, and the `artificial_analysis_*` task handlers own benchmark ingestion, cached D1 storage, derived scoring, and source attribution for model analysis data.
- **Model policy seam**: `packages/schemas/src/model-defaults.ts` holds central auxiliary and capability references, while `apps/api/src/lib/providers/models/policy.ts` derives the executable model set and resolves account-aware defaults. Provider configuration first determines what is visible; active status and Free, Pro, or BYOK entitlement then determine what may execute. The `/models` catalogue marks each entry with account-specific `isExecutable` and the effective chat default with `isDefault`. Web and iOS repair persisted selections when `isExecutable` is false, then consume the default marker or send `model_router_mode: auto` without a hard-coded model. Explicit IDs, auxiliary selectors, realtime, and sandbox execution must pass through the same active and access checks. Deprecated entries may remain for migration and historical display but cannot execute. Catalogue tests require every central policy reference to resolve to an active model from its declared provider. See ADR 0030.
- **Chat stream contract seam**: `packages/schemas/src/chat-stream.ts` owns the shared SSE formatting, parsing, and frontend assembly contract for streamed assistant messages, reasoning, tool calls, and tool results. API emitters and frontend stream consumers should use this contract instead of maintaining parallel stream state machines.
- **Chat library layout**: `apps/api/src/lib/chat` groups by responsibility rather than by file. `core/` orchestrates a request, `agent/` runs the turn engine, `preparation/` and `validation/` build and gate the request, `messages/` owns message shape and content, `streaming/` owns SSE emission and response assembly, `tools/` owns tool execution and continuation, and `policy/` owns the limits a turn runs under. Put a new module in the folder that names its responsibility; only a feature entry point belongs at the top level. Generic helpers belong in `apps/api/src/lib` or `apps/api/src/utils` instead — the directory has no `utils` catch-all, and reintroducing one is the failure mode this layout exists to prevent.
- **Request preparation seam**: `apps/api/src/lib/chat/preparation` turns a validated request into a `PreparedRequest`. `RequestPreparer` orchestrates and owns concurrency; each step it calls is a module — `model-configs.ts`, `message-store.ts`, `system-prompt.ts`, `skills.ts`, `provider-context.ts`, `goal.ts` — and holds no request state of its own. Add a preparation step as a module and call it from the orchestrator rather than growing `prepare`. Steps that only enrich a turn (skills, memory, goals, connectors) degrade to a default on failure; only a missing model configuration or validation context fails the request.
- **Async invocation seam**: `apps/api/src/lib/async/asyncInvocation.ts`, `apps/api/src/services/completions/async/handler.ts` and `AsyncMessagePollingHandler` own provider work that finishes after the turn does. Providers return the placeholder as message content parts and the metadata on `data.asyncInvocation`; persisting that message is what queues the polling task, so anything that drops the placeholder silently kills the whole chain. Provider mapping in `agent/provider-io.ts` must accept content parts as well as strings.
- **Turn durability seam**: `apps/api/src/lib/chat/core/chat-stream.ts` and `apps/api/src/lib/chat/streaming/emitter.ts` own the turn's independence from its connection. The run is handed to `executionCtx.waitUntil`, the SSE writer treats a cancelled reader as detachment and keeps the run going, and both streams heartbeat with `: ping`. Nothing on this path should treat stream cancellation as the end of a turn. See ADR 0024.
- **Turn cancellation seam**: `apps/api/src/lib/chat/streaming/turn-cancellation.ts` owns the KV-backed stop flag and the detached-only watcher that reads it. Stopping is explicit — the composer posts to `/chat/completions/:id/cancel` before aborting — because detaching no longer stops anything. A connected turn never reads the flag.
- **Stream render cadence seam**: `apps/app/src/lib/chat/stream-progress-coalescer.ts` owns how often streamed text reaches the renderer. A text delta carries the whole accumulated message, so a newer delta supersedes an older one and only the latest is delivered per animation frame; tool results, assistant metadata, and the final message flush the pending text first and then pass through in order. `useStreamingResponse` stops the coalescer in a `finally` around the stream call, so an aborted or failed turn flushes its last delta and leaves nothing scheduled. `ChatService` still reports every delta — cadence is the app's decision, not the transport's. `component-content`'s markdown renderer highlights from the fence language rather than `rehype-highlight`'s `detect`, so an unlabelled block renders unhighlighted instead of scoring every registered language on every delta.
- **Turn recovery seam**: `apps/app/src/lib/chat/turn-recovery.ts` owns re-attachment after a stream fails. It polls the completion for an assistant message that was not there before, rather than resuming the stream. `useStreamingResponse` uses it only for transport failures: an `ApiError` is a definitive answer from the server and is reported instead. `apps/mobile/ios/Polychat/Services/TurnRecovery.swift` mirrors it for iOS, where `StreamFailureClassifier` draws the same line: a `URLError` is a dropped connection worth polling through, an `APIClientError` is the server's answer, and a cancelled task recovers nothing.
- **Chat execution request seam**: `apps/api/src/lib/chat/core/execution-request.ts` owns the provider request and stream post-processing option shapes after validation, preparation, compaction, and context pruning. `ChatOrchestrator` should use this seam for buffered, streamed, and model-ensemble execution so tools, enabled tools, approved tools, delegation, recipe options, and memory-aware prepared state stay consistent.
- **Conversation compaction seam**: `apps/api/src/lib/session/SessionManager.ts` and `apps/api/src/lib/session/compaction.ts` own compaction planning, snapshot creation, summarisation, and archive persistence. Provider-facing chat paths should use `apps/api/src/lib/chat/messages/provider-mapping.ts` so compaction status rows and other display-only markers are filtered consistently.
- **Turn engine seam**: every chat turn runs through `runAgentLoop`, and streaming is a transport rather than a pipeline. `apps/api/src/lib/chat/agent/turn-transport.ts` resolves one model turn either buffered or streamed, `provider-stream.ts` parses provider events, and `assistant-turn.ts` persists and announces the result identically for both. `apps/api/src/lib/chat/policy/step-budget.ts` resolves the step budget from the request ceiling, recipe and connector defaults, and the mode ceiling. `core/model-ensemble.ts` composes multi-model runs on top of the same engine. Do not add a second way to run a turn (ADR 0022).
- **Conversation title seam**: `apps/api/src/lib/chat/agent/conversation-title.ts` names a conversation from the message that opened it, in parallel with the answer rather than after it, and `apps/api/src/lib/conversation/title-source.ts` holds the rules that decide when. A stored opening turn is titled when its title is still the excerpt written at creation; anything else — a rename, a recipe title, a conversation already under way — is left alone. ## Data Flow

- The web app initialises global providers in `root.tsx`, routes through `routes.ts`, and renders thin page modules that compose feature modules. Chat and Work share core conversation infrastructure but own separate navigation and entry points. Work routes share a persistent `/work` layout and `WorkDataProvider`, so workspace navigation and current workspace/project queries survive sibling-page navigation while TanStack Query owns freshness and mutation cache updates.
- Chat mode flows through `/chat`, canonical conversation routes at `/chat/:completionId`, `ChatSidebar`, `ConversationPage`, `ConversationThread`, `useChatManager`, React Query hooks, Zustand stores, and `apiService`. Legacy `completion_id` query links remain readable, while conversation navigation writes the path form so refresh restores the selected conversation. Its conversation list contains only creator-owned conversations without a project. One sidebar menu owns the list's status, last-activity window, grouping, and sort. The client resolves the activity window against its own calendar and sends `/chat/completions` an absolute `updated_after` timestamp alongside `archived` and `sort_by`, so the stored and device-local lists cut at the same instant and the API never has to guess a timezone; grouping stays on the client, and the choices persist in `uiStore` so the list survives navigation. A sibling actions menu archives or restores every conversation matching those filters through `PATCH /chat/completions`, which only moves rows not already in the requested state; it is withheld under the mixed `all` status because the count it shows would not describe what changes.
- Work mode flows through `/work`, `WorkSidebar`, workspace and project React Query hooks, and nested workspace/project routes. The project overview can start and auto-submit a new conversation directly, while loading persistent context before that first message. A project chat sends `metadata.project_id`; the backend verifies current workspace membership, resolves an explicit project memory scope, loads relevant project memories through the shared memory manager, loads project instructions and capabilities, and rejects attempts to attach an existing personal conversation to a project. Automatic classification and memory tools store into that same project scope. Composer actions preserve project metadata when recipes contribute request options, project uploads persist as project Sources, and people may add compatible project Sources as bounded message context. App launches stay below the project route hierarchy.
- Workspace invitations return the raw token only in the invite URL, persist its SHA-256 hash, expire after seven days, and bind acceptance to the invited email. Acceptance creates or updates the workspace membership and consumes the invitation token.
- Apps and recipes have no global product routes. Recipe management lives in Capabilities, which exists in both Chat and Work; enabled experiences cover notes, article reports, podcasts, Replicate predictions, model training, Strudel patterns, and saved outputs. Their catalogue metadata comes from the backend, while the Work runtime adapters mount the original Polychat feature components with project-scoped data hooks and navigation.
- Personal chat and Work share the same persistence vocabulary: input material becomes a source, generated or authored results become outputs, external authority stays in provider connections, reusable configuration becomes a template, and execution history is projected as activity. Project scope adds collaborative access and audit records without creating a parallel storage system.
- Remote chat requests go through `ChatService.streamChatCompletions`, the API Worker `/chat/completions` route, backend completion modules, provider adapters, repositories, and streamed response events.
- Personal Chat Live controls read authenticated `/realtime/providers`, combine registry-owned descriptors with browser protocol adapters, and reconcile provider and default model together. Work does not currently expose Live controls; the contract carries no project-specific state so a future Work consumer can share it. Provider-key mutations invalidate both model and catalogue queries, while starting a session still revalidates the provider, model access and credentials through `/realtime/session/:type`; cached discovery state never grants authorisation.
- When a model needs a capability, it may call `discover_capabilities`; the backend returns scope-aware readiness facts and the exact invocation tool. An eligible native tool, recipe gateway, or connector gateway is activated for later steps of the same response, while the normal tool response renderer offers explicit in-place setup for valid recipe or connector references. The model calls a tool only when the result says it is available now and otherwise explains the stated setup requirement. Setup continues through the existing authenticated APIs and the model does not receive the resulting credentials or authority. Work connector invocation revalidates membership and derives its provider and operation allowlists only from project-enabled recipes.
- Local-only chat requests use browser storage and optional WebLLM modules instead of backend persistence.
- Sandbox requests originate in the web app or GitHub webhook flow, are coordinated by API sandbox modules, then execute in `apps/sandbox-worker` with SSE progress.
- Training requests originate in the web app, are validated and authorised by the API Worker, then delegated to `apps/training` through an internal Worker interface.
- The scheduled models.dev sync updates checked-in model configs, then calls the API admin task trigger. The API queues Artificial Analysis ingestion, stores the Free-tier language model data server-side, and schedules derived scoring one hour later.

## Architecture Review Defaults

- Treat route and page files as orchestration modules. If logic includes parsing, state machines, measurement, timers, retries, validation rules, or more than roughly 25-40 lines, move it behind a deeper module.
- Prefer existing shared seams before creating new ones: `routeBuilder`, `ServiceContext`, repositories, provider capability registrations, `fetch-wrapper`, React Query hooks, `localChatService`, shared schemas, `agent-core`, and `library-registry`.
- Enforce Work access through workspace membership on the server. Do not treat a project or conversation ID, frontend route nesting, or `created_by` field as proof of authorisation.
- Keep global apps and recipes routes removed. Add reusable capability discovery or execution to Chat or a project library instead of rebuilding a third product mode.
- Add generic frontend helpers under `apps/app/src/lib` or an existing subfolder, not inside pages or feature modules.
- Add generic backend helpers under `apps/api/src/lib` or `apps/api/src/utils`, and keep persistence logic in repositories.
- Build `@ngriffin_uk/polychat-schemas` before validating consumers that import generated package output.
- Use focused workspace validation first, then broaden only when the change crosses multiple apps or packages.
