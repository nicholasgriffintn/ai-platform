# Architecture context

Use this map to locate current responsibilities. Read the relevant [ADR](decisions.md) for rationale; provider lifecycle 0038 and governance 0040 remain accepted designs awaiting implementation. Project Workbench 0043 is implemented as a web presentation boundary, with deeper evidence views extending it incrementally.

## Vocabulary

| Term                           | Meaning                                                                                                                                             |
| ------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chat / Work                    | Personal conversation and collaborative workspace modes sharing one conversation runtime.                                                           |
| Workspace                      | Membership and role boundary for collaborative work. Work requires its account entitlement as well as membership.                                   |
| Project                        | Shared instructions, conversations, context, capabilities and tasks inside a workspace.                                                             |
| Project Workbench              | Responsive presentation of a coding-enabled project conversation in Work; not a mode, route, runtime or persisted resource.                         |
| Capability                     | An app, recipe, skill, connector, agent or tool. Configuration, enablement and authorisation are distinct.                                          |
| Experience / app               | A rich workflow from `/capabilities`; an experience with an owning capability is presented as an app. `apps/*` instead means deployable workspaces. |
| Scope                          | Personal or project ownership passed to shared components and services. Agents additionally support workspace ownership.                            |
| Source / output                | Durable input / result. A project ID makes the resource collaborative; a conversation link adds provenance.                                         |
| Provider connection            | A person's external authority. Work does not inherit another member's credentials.                                                                  |
| Skill / agent                  | Loadable instructions / a saved persona with capability requests. Neither grants execution permission.                                              |
| Task / flow                    | Durable project work with its own conversation and goal / ordered execution stages. Distinct from the internal `tasks` queue.                       |
| Attention / inbox              | Current task state needing a person's awareness / its per-person read and dismissal projection. Neither grants task authority.                      |
| Activity / audit               | User-visible execution history / immutable workspace governance history retained after deletion.                                                    |
| Attention                      | Global, membership-filtered projection of actionable, active, failed and recent task or run state; not stored workflow state.                       |
| Conversation organisation      | Per-user pin, unread and snooze state plus personal or project-scoped labels; never access or execution authority.                                  |
| Recipe schedule                | Repeatable recipe installation trigger whose occurrences run as tasks and produce attributable conversations.                                       |
| Credit / reserve / reservation | Metered allowance / plan grace beyond the allowance / held estimate for work not yet settled.                                                       |

## Conversation execution

`lib/chat/core` orchestrates requests. `validation` and `preparation` establish model, scope and prompt state; `agent` runs the shared loop; `messages`, `streaming`, `tools` and `policy` own their named responsibilities. Keep feature internals out of the top-level orchestrator.

Both streamed and buffered turns use common finalisation and goal policy. Turn completion owns persistence, connector cleanup and lock release. Every authenticated stored execution receives a persisted `run_<id>` and versioned command receipt independent of its conversation, messages, model steps and tool calls. Runs move through accepted, running, waiting, cancelling and immutable terminal states; attempt-fenced transitions prevent stale completion. Conversation detail exposes `latest_run`, messages and project tasks may reference it, and authorised status reads use personal ownership or current project membership. Older clients may omit command and run IDs, but only explicit command IDs make retries idempotent. See [ADR 0056](decisions/0056-persist-chat-run-identity.md) and [ADR 0057](decisions/0057-order-chat-run-events-with-snapshot-reset.md).

Disconnection detaches SSE; it does not finish the run. Web and iOS resolve a lost receipt from the submitted command, anchor an authorised exact-run snapshot, then poll ordered events after that snapshot’s cursor every two seconds. Lifecycle writes and message references share the run’s monotonic sequence and a bounded 500-event retained window. A retention gap, invalid cursor, oversized stream event or non-contiguous page explicitly replaces client state with an authoritative snapshot; duplicates, stale attempts and terminal regressions are ignored, while unknown or newer protocol events fall back to snapshots. Cancellation names the run and observed attempt, is idempotent per command, and distinguishes `cancelling` from owner-confirmed `cancelled`; stale attempts cannot stop a successor. The owner checks cancellation between model and tool safe points, so an in-flight external effect is allowed to settle before the run stops. Interactive stored Chat remains best-effort Worker continuation and local-only Chat remains device-private.

`packages/schemas/src/chat-stream.ts` owns the provider-neutral stream vocabulary. `lib/chat/streaming` emits ephemeral turn activity for model steps, reasoning, response generation, tool input and execution, waits and terminal outcomes. `packages/library-chat/src/turn-activity.ts` projects that vocabulary for shared web conversation surfaces; iOS keeps an equivalent native projection over parsed Polychat events. Activity is presentation state, not execution authority or durable history: connector approvals and persisted tool results remain in their existing server Modules, and detached recovery still reads stored messages rather than replaying activity events.

Queue-dispatched stored project tasks are the durable execution cohort. The queue task holds a renewable persisted owner lease, and both task settlement and project-task state commits compare that owner. Redelivery reconciles persisted success or a waiting interaction, but marks mid-run owner loss interrupted rather than replaying model or tool work. Waiting interactions are recoverable for seven days. Run-keyed credit reservations and connector cleanup records let a successor settle resources after owner loss.

Authorised project-task detail projects the latest current-run question or approval as protocol version 1 interaction state. Its stable envelope retains structured prompts, options, written-answer support, exact tool approval context and acknowledged outcomes; `pending`, `resolved`, `expired` and `interrupted` remain distinct. Web and iOS submit through the existing exact-task endpoints, which recheck current membership and the pending interaction under the conversation lease. Native submission state is local and temporary, while task detail remains authoritative. Streamed iOS tool-result parts retain raw structured data instead of reducing interaction payloads to display strings. See [ADR 0058](decisions/0058-project-native-task-interactions.md).

The same task-detail read exposes a newest-first protocol version 1 activity projection reconstructed from project-and-task-scoped runs, bounded run events, run-keyed message parts, goal progress, interactions and completions. Proposed outcomes remain visibly distinct from actual execution; run snapshots cover legacy or trimmed journals. The shared presentation contract carries safe summaries and open event types, not reasoning, tool arguments or raw tool results. Web owns expandable detail in `component-workspaces`; iOS keeps a compact summary above the transcript and validates task scope before replacement. See [ADR 0059](decisions/0059-reconstruct-project-task-activity.md).

Task attention is a versioned projection of current authoritative task state, not a second task lifecycle. Pending decisions and meaningful failures are visible to current workspace members, assignments to the current assignee, and completions for 30 days to the creator or assignee while they remain members. Per-person read and dismissal receipts are keyed by task attention version and never mutate task state or execution authority. Web and iOS resolve notification links through the server before opening current task detail, so membership removal, later transitions and old deliveries become harmless stale links.

Notification preferences, device registrations and delivery outbox records have separate ownership. A registration belongs to one user, platform and installation; replacing a push token or browser subscription updates that installation while an endpoint fingerprint prevents cross-account reuse. Destinations are authenticated-encrypted with `PRIVATE_KEY`, and only the fingerprint is indexed. The outbox deduplicates each registration and task version, then rechecks membership, current attention state, preference and registration immediately before delivery. Provider payloads contain generic copy plus current identifiers and a server-resolved path, never task detail, tool arguments or private reasoning. See [ADR 0063](decisions/0063-project-current-attention-and-notification-delivery.md).

`services/conversations/coordinator/client.ts` serialises history mutations at their entry points. The lock is non-reentrant and uses an opaque owner token, a five-minute lease and one-minute renewal. Only the current token can renew, pass a write fence or release; absent or unreachable coordination refuses mutations, while an abandoned lease becomes available after expiry. `lib/conversation/write-fence.ts` is the persistence-boundary contract reused by the conversation manager. Tool-result compaction removes JSON formatting whitespace before provider calls without changing values, protocol fields or stored history; it has no settings or saved policy. `lib/session` owns history compaction: a snapshot records the exact message IDs fully represented within its bounded summary input, and one D1 batch inserts the snapshot and marker, archives only that covered prefix, and refreshes conversation metadata. Later candidates, non-text messages and individually oversized messages remain active; provider failure stores the covered input as a verbatim fallback transcript. Display-only compaction and goal markers stay out of model input. Async provider jobs use `lib/async` and polling handlers, with terminal writes taking the same lock.

Before every model step, `lib/chat/policy/context-budget.ts` reserves requested output capacity or 15% of the current model window, preserves system/developer instructions and the latest user-controlled message, and then fits the active summary and newest complete assistant/tool units. Provider copies of tool results above 6,000 characters use bounded head-and-tail excerpts; stored messages remain unchanged and authorised message reads retain the full result while retention permits. The exact run attempt stores a protocol version 1 context snapshot with included and omitted counts, source and approval references, effective model/provider and skills, active summary and reported-or-estimated input usage. Resuming a waiting run clears its prior snapshot. Web and iOS present the same optional contract; local-only chat remains device-private and receives no server run snapshot. See [ADR 0060](decisions/0060-budget-and-report-run-context.md).

Durable outputs snapshot bounded protocol version 1 provenance: origin, producing run and attempt, effective model/provider, loaded skill revisions, source references and approval outcomes. Content revisions copy that immutable snapshot. Authorised detail retrieval resolves each source against current authority and reports unavailable references without a link; output lists and public shares omit provenance. Legacy rows remain explicitly legacy, and producers with incomplete execution facts record partial provenance. See [ADR 0064](decisions/0064-snapshot-effective-provenance-on-durable-results.md).

Output history is append-only. A supported restore copies an earlier title and structured content into a new revision while preserving current status, sensitivity and provenance, recording its actor, parent and restored-from lineage, and atomically auditing project restores. Expected-revision fencing and current membership protect concurrent and project writes. Only article analysis/report/summary, notes and Strudel patterns are reversible; files, provider jobs, connectors, publications and sandbox repository effects remain comparable but review-only because a local row cannot compensate their external effects. See [ADR 0065](decisions/0065-append-safe-local-output-restores.md).

Each project task is a stable plan and snapshots its selected saved flow before execution. Accepted runs persist the exact flow-stage ID; completions and outputs retain the producing run, attempt and provenance. Authorised task detail projects stage state only from those records, so unexecuted stages remain proposed and interrupted attempts remain distinct from later successful attempts. Dispatch failures and model-only failures can resume at the same snapshot boundary, while a consumed external-operation approval requires reconciliation instead of a blind retry. Plan inputs are editable only before execution, and executed plans cannot be reopened or deleted. Older tasks without stage identity use an explicit unattributed task stage rather than a current-flow guess. See [ADR 0066](decisions/0066-snapshot-project-flows-and-derive-stage-evidence.md).

`lib/chat/policy/provider-retry.ts` owns model retry classification, delay and run-wide attempt accounting. Provider and gateway calls make one network attempt; the turn boundary permits one repeat per eligible call and at most two repeats across a run. Retry state is attempt-fenced, persisted and ordered for web and iOS. Cancellation interrupts the wait, while a failure after streaming begins remains terminal. Connector execution classifies a post-invocation write failure as definitively not applied or unknown: only a definitive rejection or an explicitly idempotent unknown outcome may repeat once with identical parameters. A non-idempotent unknown outcome requires external reconciliation. See [ADR 0061](decisions/0061-bound-model-retries-and-surface-unknown-writes.md).

Model and capability catalogue responses carry short-lived, versioned readiness facts with distinct ready, setup, unavailable and unknown states. They explain likely account, plan, credential and policy blockers but never authorise execution; model selection and capability execution re-check current server authority. Web and iOS preserve an invalid saved selection instead of substituting another model. A model change targets the next run, retains compatible attachments and stored conversation history, and clears model-specific response settings. Active runs and their approvals or questions block a change, incompatible attachments must be removed, and one-turn image generation with existing history requires a new conversation. Branches and multi-model responses remain the comparison mechanisms so alternatives keep separate model, run and usage identity. See [ADR 0062](decisions/0062-expire-readiness-and-make-model-handoffs-explicit.md).

Managed tool selection starts small and activates eligible tools after discovery or skill loading. Project grants constrain that activation. Saved agents layer personas into the generated prompt and request tools/skills within the runner's scope. Project tasks use the same engine, with exact dispatch and run identity plus durable question, approval and stage-completion records.

## Project Workbench boundary

ADR [0043](decisions/0043-project-workbench-presentation.md) defines the implemented presentation boundary. A Project Workbench has no server identity: it composes one project conversation with its attached sandbox runs and, when applicable, the project task that owns that conversation. A conversation can have many runs; a run need not belong to a task; Sources and Outputs retain their existing ownership and use conversation links only as provenance.

The five durable pane meanings are Conversation, Activity, Changes, Files and Proof. Conversation is always present. Activity is the selected run's event projection, distinct from project-wide Activity. Changes and Files expose authorised run evidence, not new collaborative resources. Proof renders the API-owned terminal run manifest and may later compose task evidence and linked Outputs; it becomes an Output only through an explicit save operation. Command output belongs to Activity rather than a separate Terminal pane. Preview is an optional, run-scoped review pane when a declared network service exists; it is not a sixth resource type.

`packages/schemas/src/sandbox.ts` owns the versioned terminal manifest and worker proof-evidence shapes. The sandbox worker reports repository, change, validation and delivery evidence; `services/apps/sandbox/run-manifest.ts` combines it with authoritative run state, and `run-artifacts.ts` stores bulky evidence as private Outputs with stable identities before attaching compact authorised references. Infrastructure usage can arrive before or after terminal persistence and is folded into the same manifest. Web renders that manifest directly; it does not infer success from missing evidence. iOS decodes the same compact manifest for its native Proof destination rather than copying its rules into a separate contract.

`packages/library-chat/src/run-activity.ts` projects the existing conversation trace and ordered sandbox event array into one display sequence. New worker events carry producer timestamps; source order remains the deterministic fallback for legacy evidence. The projection collapses command and validation output into lifecycle entries, derives duration only from recorded boundaries, ignores reasoning fields and redacts recognisable credentials before display. `packages/component-conversation/src/RunActivityPanel.tsx` renders that projection with detail, output, cost and latency collapsed by default.

`routes/apps/sandbox/runs-lifecycle.ts` exposes authorised reads of the coordinator's ordered event and instruction envelopes and compare-and-set updates to its existing control record. `services/apps/sandbox/runs.ts` separates project visibility from runner-only steering. Operator instructions use stable idempotency keys; expired or already-resolved approvals and stale control revisions return conflicts. The sandbox worker continues to consume instructions through `run-control-client.ts` and applies pause, resume and cancellation only through `execution-control.ts` checkpoints—there is no second conversation channel or client run state machine.

ADR [0045](decisions/0045-require-explicit-sandbox-delivery-policy.md) replaces the project commit toggle with an API-owned delivery policy. `packages/schemas/src/sandbox-delivery.ts` owns its modes and conservative legacy resolution; the project row persists the explicit JSON policy while retaining the old boolean only as a derived rollback shadow. New configuration defaults to a review branch and pull request. Custom instructions affect local preparation only, and direct delivery accepts only an existing non-`main`, non-default, non-protected branch.

The sandbox worker validates first, creates a commit only for a commit-producing policy, then requests exact approval before any push. The approval names the repository, action, branch, target, commit and validation outcome. `services/sandbox/worker.ts` resolves a current GitHub App token against both the initiating runner and configured repository, while `apps/sandbox-worker/src/lib/github-delivery.ts` rechecks direct-branch protection at the write boundary and records push or pull-request failure as run evidence. Project policy, GitHub installation authority and approval remain independent.

ADR [0046](decisions/0046-version-sandbox-environment-preparation.md) gives a project coding environment an optional, versioned setup contract. `packages/schemas/src/sandbox-environment.ts` owns the common definition and fixed `.polychat/environment.json` convention. Polychat configuration is snapshotted into the queued run; repository configuration is read from the cloned revision. `apps/sandbox-worker/src/lib/environment-setup.ts` resolves a content revision, verifies declared runtimes through fixed commands, applies setup or resume commands sequentially through the existing command and approval policy, and emits bounded redacted evidence before the agent loop begins.

Proof records setup source, configuration revision, effective setup or resume mode, terminal status, requirements and duration. Project configuration contains no credential values and does not grant access to a future secret mount or cache. Resume is an execution input over the same definition; snapshot reuse may select it only after separately proving cache compatibility and authority.

ADR [0047](decisions/0047-scope-and-invalidate-sandbox-environment-snapshots.md) stores one opaque environment snapshot handle and generation on the API-owned project row. `packages/schemas/src/sandbox-cache.ts` separates that internal record from the client summary. The worker derives a deterministic key from the project, runner, GitHub installation, repository revision, lockfile blobs, setup revision, runtime requirements, generation and platform version; only an exact match can select resume preparation.

`services/workspaces/environment-cache.ts` resolves project-owned cache input, invalidates it and persists terminal candidates through conditional repository updates. Rebuild and delete remain nested project actions. A generation change prevents an active run from restoring deleted state into the project record, the first concurrent candidate for a key wins, and a failed or expired restore cleans the clone before full setup. Backup handles never enter stored run data, coordinator events or client responses; Activity and Proof receive only age, outcome and provenance.

ADR [0048](decisions/0048-supervise-declared-project-services.md) extends that environment definition with optional run-scoped services. `packages/schemas/src/sandbox-services.ts` owns names, repository-relative working directories, commands, dependency graphs, declared ports, health checks, startup timeouts, restart policy and compact evidence. The project environment remains API-owned configuration; the queued run snapshots it, and it grants neither process authority nor access to another member's credentials.

`apps/sandbox-worker/src/lib/service-supervisor.ts` validates the manifest and command policy at execution, resolves real checkout paths, rejects occupied declared ports, starts and stops in dependency order, checks health and caps automatic restarts. It emits bounded redacted logs and lifecycle events through the existing run coordinator and records compact terminal evidence in Proof. Start, restart and stop are runner-only `service_action` instructions on the existing run endpoint; there is no terminal channel, process route or client-owned service state.

ADR [0049](decisions/0049-gate-sandbox-previews-through-current-project-authority.md) adds that separate preview boundary without creating another runtime. `packages/schemas/src/sandbox-preview.ts` owns the short-lived access, state and internal gateway contracts, while `internal-service-auth.ts` owns the narrow service-principal contract. `services/apps/sandbox/previews.ts` creates, reads, revokes and authorises preview sessions only after current project-run access and healthy declared-service checks; `preview-grants.ts` signs purpose-bound grants, while the existing run coordinator stores the private forwarding token and consumes the bootstrap once.

`apps/sandbox-worker/src/lib/preview-gateway.ts` serves opaque wildcard origins, exchanges the one-time bootstrap for a host-only cookie and re-authorises every HTTP request and WebSocket data message through the API service binding. Each call uses a short-lived `sandbox-preview:authorise` service principal and enters the normal API middleware and route-builder path at `routes/apps/sandbox/preview-authorisation.ts`; `index.ts` contains no preview dispatch. The gateway forwards only the session's declared port through the Sandbox SDK, constrains redirects and message size, strips credentials and upstream cookies, and replaces response security headers. Run-terminal and non-healthy service events revoke stored sessions; current membership loss fails the next authorisation. Container addresses, SDK URLs, forwarding tokens and durable-object identities do not enter public contracts or logs.

The API owns preview identity, scope, expiry, revocation and health state. Clients may derive only presentation such as whether to show loading, an expired explanation or a refresh action. Preview access permits an authorised project read; it does not imply runner steering, connector credentials, GitHub authority, command approval or agent-driven browser control.

`packages/component-workspaces/src/ProjectWorkbench/ProjectWorkbenchPreview.tsx` owns the router-free trusted controls, responsive viewport presets and untrusted frame boundary. `apps/app/src/hooks/useProjectWorkbenchPreview.ts` joins run service evidence to the preview API without persisting authority locally. The host formats route, viewport, optional normalised region or user-authored element reference and bounded annotation through `lib/project-workbench-preview.ts`, then submits it as the existing runner-only `message` instruction. The API records the submitting user on that instruction and its receipt event; there is no DOM bridge, image store, review-feedback table or second chat channel.

`apps/app/src/hooks/useProjectWorkbenchEvidence.ts` selects the referenced diff Output and `lib/api/bounded-response.ts` stops text reads at the presentation limit. `packages/component-content/src/RunEvidence/` owns unified-diff parsing, review order, changed-file navigation and bounded artefact previews. It receives content and load actions from the host, has no API authority of its own and never treats a storage key or model-supplied path as access.

The API remains authoritative for project coding configuration, resource associations, run and task state, event order, pending interactions, artefacts, Sources, Outputs and authority decisions. Clients derive eligibility and presentation from those records: selected run and pane, readiness and attention labels, pane badges, proof grouping, diff preferences, collapsed sections and responsive layout. A current coding environment enables new runs. An attached historical run keeps the workbench readable after that configuration is removed; a conversation with neither uses the ordinary Work conversation presentation without disabled coding chrome.

Web may keep Conversation beside one supporting pane, while narrow web and iOS may use a drawer or full-screen destination. They consume the same wire meanings without sharing layout code. Membership permits authorised project reads; the initiating runner's current account, usage and GitHub App authority permits dispatch; connector credentials remain personal; each approval retains its exact pending action and actor policy. None implies another.

## Global Attention boundary

ADR [0050](decisions/0050-derive-global-attention-from-authoritative-work-state.md) defines Attention as a derived operational read model, not another resource or workflow. `packages/schemas/src/work-attention.ts` owns the shared kinds, filters, item and pagination response. `apps/api/src/repositories/AttentionRepository.ts` joins current membership to project tasks and sandbox Activity records, applies stable ordering and exact filtered counts, and returns facets only for currently eligible work. `services/attention/` exposes that read model from the existing workspace API; the task-only endpoint remains for narrow project summaries.

`apps/app/src/lib/work-attention.ts` owns URL parsing and destinations, `hooks/useWorkAttention.ts` owns the query and `components/Work/AttentionPage.tsx` composes the router-free `packages/component-workspaces/src/WorkAttentionView.tsx`. Filters are URL-addressable local presentation state. Resolution remains on the existing task, conversation or Activity surface and retains its authority; Attention grants no approval, runner or connector capability.

## Conversation organisation boundary

ADR [0051](decisions/0051-separate-personal-conversation-state-from-project-labels.md) keeps reading workflow personal while sharing only deliberate project taxonomy. `conversation_user_state` owns per-user pin, unread and snooze values with a compare-and-set revision. `conversation_label` owns either a personal-user or project scope, and assignments link those labels to conversations without changing conversation access.

`packages/schemas/src/conversation-organisation.ts` owns the wire contract. `ConversationOrganisationRepository` owns persistence and effective next-response detection; `services/conversation-organisation/` owns current conversation access, scope matching and project-role checks. Personal and project conversation repositories project organisation into their existing lists, global search includes it for discovery and reversal, and Attention excludes active snoozes while retaining authoritative task and run meanings.

`apps/app/src/hooks/useConversationOrganisation.ts` owns remote state and invalidation. `components/ConversationOrganisationDialog.tsx` adapts it to the router-free shared dialog in `packages/component-navigation`; Chat and Work sidebars provide the applicable personal or project scope. Organisation never grants membership, runner actions, connector credentials or approvals.

## Recipe schedule boundary

ADR [0052](decisions/0052-keep-repeatable-scheduling-in-recipes.md) keeps repeatability in recipe installations. `packages/schemas/src/apps.ts` owns recipe trigger contracts; a schedule trigger carries its cron expression, prompt, enablement and optional notification delivery. The installation owner remains the charging user and supplies any connector credentials used by a run.

`services/apps/recipes/scheduler.ts` is the only user-work due scanner. It enqueues deterministic `recipe_execution` tasks through `TaskService`; `RecipeExecutionHandler` revalidates the installation and project capability before invoking the configured recipe. Each occurrence produces an attributable conversation rather than resuming or making the conversation itself repeatable.

Web manages schedules through the existing recipe capability and project Scheduled recipes surfaces. Conversations may show recipe-run provenance, but Chat and Work conversation lists do not create, update or own schedules. There is no conversation-schedule contract, table, route, repository, task type or client state.

## Data and authority

Authorise project reads and conversations through current workspace membership; apply each resource's management roles separately. Keep private files behind Source/Output access and resolve their bytes server-side before provider calls. Project context is curated explicitly, and built-in memories are owned by the memory service.

Authored skills use D1 identity and stable/draft pointers with immutable private R2 bundles. Pin one stable revision per request while revalidating access on each load. Retrieval similarly uses provider matches only as candidates: active scoped D1 records authorise content, and immutable vector provenance governs cleanup.

Composio owns configured connector credentials and tool schemas. Polychat owns scoped session handles, exact-action approvals, event mappings and cleanup. A queue record, catalogue match or model-produced argument is never authority by itself.

Credit admission reads persisted plan allowances; missing allowances refuse work. The signed-in ledger records idempotent vendor-unit spend, while anonymous actors use running totals. BYOK model/hosted-tool spend is uncharged; other metered work is not. Stored run usage groups ledger events by stable run and attempt, but keeps the admission reservation, recorded consumption and settlement distinct. Missing provider telemetry is unknown rather than zero actual consumption. The assistant-turn finaliser normally settles the hold; cancellation, failure, owner recovery and the 24-hour expiry sweep release unfinished holds through the same idempotent boundary. Workspace reporting is attribution, not a shared balance. See [usage operations](../operations/loop-cost-controls.md) and [ADR 0067](decisions/0067-attribute-run-usage-and-settle-reservations-once.md).

## Model catalogue boundary

The API model catalogue separates **families**, shared **model definitions** and provider **offerings** under `apps/api/src/data-model/models/`. Each family has one JSON file containing its description, defaults and model definitions; each provider has one JSON definition. `lib/providers/models/catalogue-definition.mts` validates and resolves family → model → provider → offering precedence, and `catalogue.ts` supplies the catalogue and provider views. `scripts/sync-models-dev/` owns conversion, upstream metadata, explicit execution corrections and generated imports. Keep current public IDs and provider ordering stable; see [ADR 0069](decisions/0069-share-model-definitions-across-provider-offerings.md) and [catalogue operations](../operations/model-catalogue.md).

## Web boundaries

`apps/app/src/lib/api/fetch-wrapper.ts` owns credentials, CSRF, timeouts and API error handling. React Query hooks own remote/local coordination and invalidation; the authenticated store owns hydrated user/settings state. `lib/local/local-chat-service.ts` owns local conversation persistence.

Keep customisation drafts in `component-account` as field-level edits over hydrated settings. Refresh untouched controls as settings arrive, preserve local edits until the server returns matching values, and discard drafts when the settings identity changes.

Chat and Work compose the same `ConversationThread` and scoped capability surfaces. Keep backend catalogue metadata authoritative and project request metadata intact. Automatic routing admits text-response chat models, excluding media generation, realtime and specialist extraction models; multimodal chat inputs remain eligible. Failed AI prompt analysis falls back to keyword requirements before scoring eligible models. Host controllers supply resolved links and actions to render packages through their existing providers.

Use shared UI primitives for buttons, dialogs, focus, overlays and reduced motion. Tool messages and parts share `ToolResultView`; declared renderers and payload shape choose the body. Presentation components emit typed, optionally asynchronous intents and only show local acknowledgement after the host action succeeds; persisted interaction state remains authoritative. Native task cards support structured question choices, written answers and exact approve/reject actions. Unknown interaction types stay visible but non-actionable. The stable task destination is `(workspaceId, projectId, taskId, conversationId?)`; inbox and push links resolve that destination against current state and access rather than treating a message as authority. Task activity uses the same project, task and run identities, with an open type plus stable category/status presentation fields that later context, retry, attention, evidence, usage and performance work can extend. Stream rendering coalesces supersedable text, yields after bounded progress batches and flushes before authoritative boundaries. Conversation detail loads the newest 100 visible messages and pages backwards under the same access check; stored output stays complete while text, JSON and table renderers start with expandable bounds. See [streaming operations](../operations/streaming-responsiveness.md) and [ADR 0068](decisions/0068-bound-live-streams-and-page-durable-history.md).

`packages/component-ui/src/styles.css` owns cross-package semantic colour tokens, one block per named theme selected by `data-polychat-theme`; `packages/component-ui/src/theme.ts` is the registry those blocks answer to and derives the pre-paint bootstrap script. Hosts map framework aliases to those tokens; feature components consume semantic roles, and identity colour for capabilities and providers resolves through the `--polychat-accent-*` scale rather than raw palette classes. Project identity renders as a colour mark beside the project name and never tints shared chrome, so an arbitrary project colour cannot fight the theme; it does not change state or authority. The same file declares the three font tokens (display, body, mono) with system fallbacks; the web host loads the house faces and maps them to the `font-display`, `font-sans` and `font-mono` utilities, and components ask for a role rather than a family.

`apps/app/src/components/Discover` owns the product tour: a registry of sections, one band per section fed by the model registry, capability catalogue, plan list and pet lore, and a lazy wrapper the home route mounts beneath the welcome screen for guests only. The `/discover` route renders the same bands as a page; `components/Sidebar/DiscoverSidebarSection` is the navigation segment that links to it. Bands read data, never hold a second copy of it, and never change state. `components/Models/ModelsCatalogue` is the public catalogue page over the same model registry, grouped through `lib/model-catalogue`; it shows what the picker knows and adds nothing the picker does not.

The same stylesheet owns shared motion durations, easing, distance and stagger values plus micro, panel, entrance, active-execution and optional ambient primitives. Keep status text authoritative: active-execution motion signals activity, never completion percentage. Reduced-motion media rules make those primitives static, while pet animation remains separately governed by its user setting; idle pet flourishes stop when work becomes active. Ambient consumers must expose `data-active-work="true"` on themselves or an ancestor so continuous decoration pauses during work.
